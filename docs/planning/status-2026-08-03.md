# Roadmap status, checked against the code

Written 2026-08-03. Every claim here was verified by reading the source, not
by trusting `00-roadmap.md` or a previous status note. Where the roadmap and
the code disagree, the code wins and the disagreement is recorded.

## The short version

M1 is largely delivered but by a different route than planned, and three of
its exit criteria are unmet. Meanwhile several M2 items shipped early,
including the two that make up the product's moat. Progress is real but very
uneven, and the unevenness is worth seeing plainly before choosing what is
next.

### Item 4 deserves its own note

The undo work was finished and unreachable, which is a failure mode this
project has hit repeatedly and should now recognise on sight. It is wired
now; the diagnosis below is kept because the pattern matters more than the
fix.

- `crates/stream/src/undo.rs`: a 210-line fixed-capacity ring, 13 functions,
  with tests.
- `crates/edit-intent/src/parse.rs:307`: "scratch that", "scratch this" and
  "undo that" parse into `EditIntent::Undo`.
- `crates/edit-intent/src/lib.rs:311`: `apply()` deliberately returns `None`
  for `Undo`, documented as "which the caller's undo ring resolves".
- `crates/outloud/src/inject.rs`: no reference to `UndoRing` or `seal_undo`
  anywhere. Nobody is that caller.

So the user says "scratch that", it parses correctly, `apply` returns `None`,
and `inject.rs:270` reports `EditNoMatch`: the app tells them the command did
not match. Every layer works and the wiring between two of them does not
exist.

This is the same shape as `vocabulary.sets` (a complete matcher no transcript
passed through) and `formatting.casing` (parsed, validated, never read).
Three instances now, all found by asking "who calls this" rather than "does
this work".

**Resolved (same day).** `deliver` now routes `EditIntent::Undo` to the ring
on both backends: macOS reads the field through the accessibility tree,
Windows through UIA's TextPattern/ValuePattern, and both then ask the same
`resolve_undo`. Recording happens at one place per backend rather than at
each transport, because the macOS side already needed five separate fixes
for "every write path must remember the extra thing".

Two structural changes so this cannot recur quietly:

- The edit decision is an `EditRoute` enum that delivery matches
  exhaustively, so an unhandled route fails to COMPILE rather than falling
  through to "that command did not match".
- `OUTLOUD_NO_INJECT` now reports the route it would have taken instead of
  returning before the decision. Previously the only way to observe edit
  routing was to speak into a live window and watch, which is precisely why
  nobody noticed. `docs/investigations/edit-intent.md` predicted this
  consequence in writing before it happened.

Undo declines rather than forcing a restore when the field changed after our
write, so it cannot destroy work done in between.

## What this means

Two of the three unmet M1 criteria are the ones the roadmap itself flagged as
sequencing risks, and both were skipped in the same way: they are
infrastructure, not features, so nothing broke visibly when they were
deferred.

1. **Signing** was scheduled for week 5 precisely because M0 proved TCC pins
   ad-hoc grants to a build's `cdhash`. Skipping it did not block progress; it
   just made every rebuild silently revoke permissions, which is exactly what
   happened repeatedly this week.
2. **The eval harness** was scheduled before more commands were added, because
   edit-accuracy plateau is a named top-5 risk. There are now 32 intents and
   no corpus measuring any of them.

The undo wiring is the cheapest real win on this list: the hard parts are
written and tested, and what is missing is the call site.
